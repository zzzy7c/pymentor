# ADR 0004 · 部署形态与沙箱边界

- 日期：2026-10-22
- 状态：**已落地**（`deploy/prod.compose.yml`、`deploy/Caddyfile`）；公网可达性**未验证**
- 触发：SPEC D12 / §5.16 / §8 R6 / §9 第 10 条

---

## 决定 1 · 单台 Linux VM + Compose + Caddy，而不是 PaaS

### 背景

本项目要执行用户与模型生成的 Python 代码。执行发生在**沙箱容器**里，由
`sandbox/runner.py` 通过 Docker API 创建；api 进程本身从不 `exec()` 用户代码。

Railway / Fly.io 等托管平台不提供 Docker-in-Docker。要在上面跑，只有两条路：

1. 放弃沙箱，在 api 进程里执行代码 —— 直接违反 `AGENTS.md` §4；
2. 换远程沙箱服务 —— 超出本阶段范围，且引入新的信任方。

### 结论

单台 Linux VM，`docker compose -f deploy/prod.compose.yml up -d --build` 起三件套：

- `api`：FastAPI + LangGraph，挂 `./data`、`./data/hf`、`/var/run/docker.sock`；
- `web`：Streamlit，只装 `[dependency-groups] web`；
- `caddy`：80/443，TLS 与反代，SSE 用 `flush_interval -1`。

沙箱镜像在**宿主**预构建（`pyassist-sandbox:1`），compose 不负责构建或启动它 ——
它是被 api 按需创建的一次性容器，不是常驻服务。

### 代价

- 单机故障即全站故障；扩容要先迁移到 PostgreSQL 并处理检查点共享。
- 备份、监控、证书续期都由运维者负责。这是自托管的正常成本，不是缺陷。

## 决定 2 · api 容器挂载 `docker.sock` 的威胁模型

### 事实

`/var/run/docker.sock` 不是"一个方便的 API"，而是**宿主 root 的通行证**。
挂载它的容器内，任何能调用 Docker API 的代码都可以创建特权容器、挂载宿主根目录，
最终取得宿主 root。

### 因此划定的边界

| 组件 | 信任级别 | 说明 |
|------|----------|------|
| `api` | **受信**（等同宿主 root） | 持有密钥、业务库、Docker socket |
| `sandbox` | **不受信** | 执行用户/模型代码；无网络、只读根文件系统、非 root、capabilities 全丢、资源/时间上限 |
| `web` | 受信但最小 | 只装 streamlit + httpx，只经 HTTP 调 api |

配套约束（全部已落地）：

1. **api 永不执行用户代码**；执行路径只有 `sandbox/runner.py`。
2. 沙箱参数固定在 `config.SANDBOX_LIMITS`，runner 不暴露旋钮；守护 #36 禁止别处构造。
3. 代码**不依赖宿主路径挂载**：容器先建立 stdin 通道，`start()` 后把
   `长度头 + 源码 + 程序 stdin` 写进去，由容器的固定引导脚本落到可写的 `tmpfs /tmp`。
   （2026-10-22 修订：原定用 `put_archive` 写入，实测在 `read_only=True` 下 daemon 一律
   返回 `400 container rootfs is marked read-only`，见下方「修订记录」。）
4. api 容器以 uid 10001 运行，只通过 `DOCKER_GID` 获得 socket 访问权，不 `chmod 666`。
5. 不把沙箱并入 api 容器，也不在这台 VM 上跑其他业务。

### 残余风险

- Docker daemon 或内核漏洞导致的逃逸不在防护范围内；
- 本项目**没有鉴权**（`user_id` 固定 `local`），公网暴露前必须加访问控制。

这些限制写进 `deploy/README.md`，而不是假装沙箱"绝对安全"。

## 决定 3 · 前端镜像不装后端依赖

### 背景

`streamlit` 曾放在 `project.dependencies` 里。api 镜像按 `uv sync --frozen --no-dev`
会把它一起装进去；web 镜像若照抄，会连带安装 torch / chromadb（约 2GB），
而前端只需要 streamlit + httpx。

### 结论

- `streamlit` 移入 `[dependency-groups] web`；
- api 镜像不装 web 组；web 镜像用 `uv sync --frozen --only-group web --no-install-project`；
- 本地开发要跑前端：`uv sync --group web`（README 已写明）。

副作用是本地 `uv sync` 不再默认安装 streamlit —— 这是刻意的：前后端依赖集合不同，
装错镜像的代价远高于多敲一个 `--group`。

## 修订记录 · 2026-10-22 · 代码怎么进沙箱容器

**触发**：`pytest -m docker` 全组 10 条失败，报
`400 Client Error ... "container rootfs is marked read-only"`。

### 实测（Docker 29.8.1 / Docker Desktop，Windows 11）

| 方案 | 结果 |
|------|------|
| `put_archive("/work", tar)`，容器 `read_only=True` | **拒绝**：`container rootfs is marked read-only` |
| `put_archive("/tmp", tar)`，落点是 `tmpfs` 挂载 | **同样拒绝** —— 拒绝发生在解析挂载之前，不是"目标不可写" |
| 匿名卷挂 `"/work": {}` + `put_archive` | 同样拒绝 |
| 宿主临时目录只读挂载到 `/work` | 可用，但**违反决定 2 第 3 条**：生产 api 在容器内，它建的临时目录在宿主上不存在，daemon 会挂出一个空目录 |
| **stdin 流送达**（`attach_socket` → `start()` → 写 payload → `shutdown(SHUT_WR)`） | **可用**：65KB 源码、程序 stdin、只读 `/work`、非零退出、traceback 全部符合预期 |

### 结论

采用 stdin 方案，落点从 `/work` 改为 `tmpfs /tmp/main.py`：

- 容器 `command` 是固定引导脚本（`runner.py::_BOOTSTRAP_SOURCE`，经 `python -c` 传入，
  **镜像文件不动**）；
- 协议 = `<源码字节数>\n` + 源码 + 程序 stdin。长度头不能用分隔符替代；
- 代码送不进去（`OSError` / 写超时）属于基础设施故障 → `SandboxError`，
  不能记成用户代码的 `status="error"`；
- `/work` 因此**真的**只读：`open("/work/...", "w")` 返回 `EROFS`（判据 ② 现在名副其实）。

`SandboxRunner` 协议、`SandboxLimits`、镜像、API 契约均未变。
