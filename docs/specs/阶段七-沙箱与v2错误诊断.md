# SPEC — 阶段七 · 沙箱 + v2 错误诊断 · 实施规格

> **归档声明**：阶段一（工程底座）、阶段二（LLM 基座）、阶段三（持久化与状态双源）、
> 阶段四（API 契约与错误体系）、阶段五（RAG 子系统）、阶段六（v1 文档问答 + SSE）
> 的规格均已归档到 `docs/specs/`：
> `阶段一-工程底座.md`、`阶段二-LLM基座.md`、`阶段三-持久化与状态双源.md`、
> `阶段四-API契约与错误体系.md`、`阶段五-RAG子系统.md`、`阶段六-v1文档问答与SSE.md`。
> 本文只描述**阶段七**。阶段六的归档件与原 `SPEC.md` **逐行一致**（`cmp` 校验通过）。
>
> 本文件是施工规格，不是契约。契约是 `AGENTS.md`；两者冲突时以 `AGENTS.md` 为准。
> 本文的每一条设计决定都能追到 `AGENTS.md` 的某个条款号或本文件的某条核实事实（§2）。

**阶段七 = 沙箱 + v2 错误诊断**（`ROADMAP.md`「阶段七 · 沙箱 + v2 错误诊断」）。
它交付 v2：**用户贴报错 → 检索文档 → 解释根因 → 给出修复 → 在隔离容器里真的跑过**。
"看起来对"不算通过，必须跑过（`AGENTS.md` §5.3）。

本阶段有**两个**与阶段六性质不同的风险：

1. **第一段真正不可信代码进入系统。** 隔离边界一旦写错，代价不是 bug，是宿主机。
   `sandbox/runner.py` 与 `Dockerfile.sandbox` 是本项目唯一的安全边界。
2. **第二张 LangGraph 图第一次同时具备「工具循环 + 结构化输出 + 沙箱回环」。**
   阶段二修好的 `reasoning_content` 补丁要在这里第二次承重（`AGENTS.md` §1 / §5.1）。

## 0. 定位与硬指标

| 项 | 值 | 出处 |
|---|---|---|
| 交付版本 | v2（错误诊断 + 代码执行） | `AGENTS.md` §0 |
| 错误类型识别准确率 | **≥ 85%**（在 `evals/datasets/errors.jsonl` 的 20 条上） | §5.3 |
| 修复后代码沙箱实际执行通过率 | **≥ 70%**（"看起来对"不算，必须跑过） | §5.3 |
| 沙箱约束 | 无网络、只读根文件系统、CPU/内存/时间上限、非 root —— **必须实测验证，不是只配置** | §5.3 |
| 恶意用例 | 死循环、`os.system("rm -rf /")`、读 `/etc/passwd`、fork 炸弹全部**不伤宿主、不崩服务** | §5.3 |
| 用户代码失败 | **不是服务错误**：报错 / 超时 / 被拒绝都以正常响应（HTTP 200 + `data.status`）返回 | §3.2 |
| 产品原则 | 宁可回答"文档里没有"，也不要编造 API；所有解释可溯源 | §0 |

**本阶段完成后，以下五件事必须同时成立：**

1. `POST /diagnose` 返回 §3.1 信封，`data.status ∈ {ok, error, timeout, rejected, unverified}`，
   `data.verification` 里的 `stdout / stderr / exit_code / duration_ms` 来自**真的容器执行**；
2. 修复代码的最终判定**只认沙箱**：`verify.status == "ok"` 才算修好，模型自己说"已修复"不算；
3. 同一 `thread_id` 从已完成检查点恢复，**不会再起第二个容器**；`sandbox_key` 相同即复用结果；
4. `uv run pytest` 全程离线且全绿；真实隔离验收由 `uv run pytest -m docker` 单独承担；
5. 诊断图在**连续两轮工具调用之后**，第三轮请求的出站 payload 里 `reasoning_content` 仍然存在。

## 4. 关键设计决定（D1–D12，施工时不可协商）

### D1 · 沙箱是**进程外 Docker 边界**，不是 Python 层过滤

`src/pyassist/**` 内**只有** `sandbox/runner.py` 允许出现：

- `import docker` / `from docker ...`；
- `client.containers.create(...)` / `containers.run(...)`；
- 容器参数（网络、只读、内存、CPU、pids、user、capability）。

其他任何文件都不得直接构造容器，也不得用 `subprocess` 去调 `docker` CLI。
守护 #34 / #35 把这条钉住；`AGENTS.md` §4 是它的契约依据。

**为什么不是"在进程里限制"**：`exec()` 与 `eval()` 在 `src/` 已被禁止（守护 #4），
而 `subprocess` 顶替沙箱在 §4 被明令禁止。隔离必须由内核提供，Python 只能做编排。

### D2 · `SandboxRunner` 契约：用户代码的失败**不抛异常**

```python
SandboxStatus = Literal["ok", "error", "timeout", "rejected"]

@dataclass(frozen=True, slots=True)
class SandboxResult:
    status: SandboxStatus
    exit_code: int | None
    stdout: str
    stderr: str
    duration_ms: int
    is_truncated: bool
    stdout_lines: int
    stderr_lines: int
    rejected_reason: str | None = None
    idempotency_key: str = ""

class SandboxRunner(Protocol):
    async def run(
        self, source: str, *, stdin: str = "", timeout_seconds: int | None = None
    ) -> SandboxResult: ...
```

- `status="error"` = 用户代码抛异常（非零退出）；`"timeout"` = 到时间上限被杀；
  `"rejected"` = 进入容器前就被策略拒绝（空代码 / 超长代码）。
- **只有沙箱基础设施故障**（daemon 不可达、镜像缺失、创建容器失败）才 `raise SandboxError`。
  `SandboxError` 基类的 `code` 是 `INTERNAL_ERROR`，经 `api/errors.py` 映射为 **500**，
  这才是"服务端故障"的语义（`AGENTS.md` §3.2）。
- `SandboxTimeout` / `SandboxRejected` 两个异常**保留但本阶段不抛**：它们的 `data` 形状
  （`{"status": "timeout", ...}`）已经被 §3.2 定义，但 `/diagnose` 的语义更适合用
  `SandboxResult.status` 直接表达。§10.3 记录这个选择。

### D3 · 输出截断在 runner 内完成

`SandboxLimits` 的 `output_head_lines=100` / `output_tail_lines=100` 是**检查点膨胀的闸门**
（`AGENTS.md` §2「检查点会膨胀」）。截断必须发生在 `SandboxResult` 生成之前，
而不是节点里、更不是服务层里 —— 否则同一份输出会在状态里存两遍。

规则（`truncate_output`，纯函数）：

1. 先按行：`len(lines) <= head + tail` 原样返回；
2. 否则保留头 `head` 行 + 一行 `……（已省略 N 行）……` + 尾 `tail` 行；
3. 再按字符：总长超过 `max_output_chars` 时保留头尾字符，插入 `……（已截断）……`；
4. `is_truncated` 为两次判断的**或**；`stdout_lines` / `stderr_lines` 记录**截断前**的行数。

### D4 · 幂等键 + 图状态缓存

```python
def sandbox_key(source: str, *, stdin: str = "", limits: SandboxLimits = SANDBOX_LIMITS) -> str:
    parts = [
        SANDBOX_IMAGE,
        str(limits.timeout_seconds), str(limits.memory_mb), str(limits.cpus),
        str(limits.pids_limit), str(limits.tmpfs_size_mb),
        stdin, source,
    ]
    return hashlib.sha256("\x00".join(parts).encode("utf-8")).hexdigest()
```

- 图状态里的 `sandbox_results: dict[str, SandboxResult]` 用**合并 reducer** `{**old, **new}`。
- 工具与 `verify` 节点都先查缓存；命中则**不再起容器**。
- 沙箱执行本身**没有持久副作用**，所以节点重试是安全的；缓存的作用是
  (a) 同一轮内 `run_code` 与 `verify` 对同一段代码不重复执行；
  (b) 从已完成检查点恢复时不重复付容器的钱。
- 局限（诚实记录）：若节点在"沙箱已跑完、状态尚未落检查点"之间崩溃，重试会再跑一次。
  这个窗口无法在没有外部去重表的前提下消除；本阶段接受，并在 `sandbox.exec` 日志里带
  `idempotency_key` 便于统计重复率（§8 R6）。

### D5 · 诊断图的形状

```
START → retrieve → agent ──有 tool_calls 且未到上限──→ tools ──→ agent
                     │
                     └──否则──→ repair → verify ──pass──→ finalize → END
                                   ↑         │
                                   └─失败且 repair_attempts < MAX_REPAIR_ATTEMPTS─┘
```

- **探索**（`agent ⇄ tools`）与**最终修复**（`repair`）是两件事：
  - 探索可以调 `search_docs` / `read_doc` / `explain_error` / `run_code`，最多 `MAX_TOOL_ROUNDS=3` 轮；
  - 修复必须产出**结构化**的 `RepairDraft`，不再走工具循环（D6）。
- **验证是图节点，不是工具**：模型不能自己宣布"修好了"；`verify` 用 `fixed_code` 真的跑一次容器，
  结果写回状态，由条件边决定是否回环。
- 两个上限：`MAX_TOOL_ROUNDS=3`（沿用）与 `MAX_REPAIR_ATTEMPTS=2`（新增）。
  到顶就 `finalize`，`data.status` 保留最后一次验证的真实结果（`error` / `timeout` / `rejected`）。

### D6 · 修复用 `with_structured_output`，**不从散文里抠代码块**

```python
class RepairDraft(BaseModel):
    error_type: str
    explanation: str
    fixed_code: str
    change_summary: list[str]
```

- `repair` 节点调 `model.with_structured_output(RepairDraft, include_raw=True)`。
  `include_raw=True` 是**必须的**：默认实现会丢掉 `usage_metadata`，pro 档的成本会整段消失（S10）。
- 禁止 `re.search(r"```python(.*?)```")` 之类的解析 —— `AGENTS.md` §3.4 明确禁止
  "自己 `json.loads` 后正则清洗"。模型没给 `fixed_code` 就抛 `LLMBadResponse`，
  不要猜一段代码出来。
- 若 U4 证实思考模式与 JSON 模式冲突：**只在 `repair` 节点**用 `thinking=False`
  的模型实例，并写 ADR（`AGENTS.md` §1 兜底条款）。

### D7 · 工具集按图取子集（**阶段六预留失效之处，必须改**）

阶段六的 `tool_specs()` 返回**全部** `TOOLS`。阶段七往 `TOOLS` 里加两个工具后，
如果 qa 图仍然拿全量，v1 的 `agent` 节点就会看到 `run_code`，而它的 `tools` 节点
**没有注入 runner** —— 模型一旦调用就是 `TypeError` / 直接崩溃。

因此：

```python
# agent/registry.py
TOOLS: Final[tuple[BaseTool, ...]] = (SEARCH_DOCS, READ_DOC, EXPLAIN_ERROR, RUN_CODE)

def tool_specs(names: Sequence[str] | None = None) -> list[dict[str, Any]]:
    """`names=None` 返回全部；否则按名字顺序取子集（未注册的名字抛 KeyError）。"""
```

- `agent/graphs/qa.py` 改成 `tool_specs(QA_TOOL_NAMES)`（一行改动）；
- `agent/graphs/diagnose.py` 用 `tool_specs(DIAGNOSE_TOOL_NAMES)`。
- 工具名常量放 `config.py`，与模型名一样只写一处。

`explain_error` 放在 `agent/tools/docs.py`：它本质是"解析报错 → 查文档"的薄包装，
与 `search_docs` 共用 `Searcher` 与编号规则；新建 `diagnose_tools.py` 会让
`AGENTS.md` §2 的目录布局多一个所有者，收益不抵成本（§9.1）。
`run_tests` **不建**：`AGENTS.md` §0 把它归 v3（§9.2）。

### D8 · `/diagnose` 是**非流式**信封接口

```json
POST /diagnose
{
  "error_text": "Traceback (most recent call last):\n ...",
  "code": "print(1 / 0)",
  "session_id": "可选，缺省用 request_id"
}
```

成功：

```json
{
  "ok": true,
  "data": {
    "status": "ok",
    "error_type": "ZeroDivisionError",
    "explanation": "... [1] ...\n\n来源：\n[1] ...",
    "fixed_code": "print(0)",
    "change_summary": ["把除数换成非零常量"],
    "verification": {
      "status": "ok", "exit_code": 0, "stdout": "0\n", "stderr": "",
      "duration_ms": 412, "is_truncated": false
    },
    "citations": [{ "index": 1, "title": "...", "section": "...", "url": "...", "snippet": "..." }]
  },
  "error": null,
  "meta": { "...": "..." }
}
```

理由三条：

1. `AGENTS.md` §5.3 的验收语言就是 **`data.status`**："用户代码报错/超时以正常响应返回"。
   §3.2 给 `SandboxTimeout/Rejected` 定的 `data` 形状也是对象，不是 SSE 事件。
2. 阶段六的 `QaEvent` / `_PAYLOAD_KEYS` 是封闭白名单，扩事件类型会改动**已发布**的线上格式（S11）；
   本阶段没有消费方需要流，不必为它付这个代价。
3. 一次诊断的模型调用次数是有限的（≤3 轮工具 + ≤2 次修复），非流式不会撞 HTTP 超时；
   若将来 UI 需要逐字看到诊断过程，在阶段八加 SSE 版（§11）。

`RetrievalEmpty` 仍然走 `raise`：`api/errors.py` 把它映射为 **200 + `ok=true`**，
`data = {"status": "empty", "query": ...}`（与 v1 `/knowledge` 同一语义）。

### D9 · `DiagnoseState` 只加字段，不改继承来的 reducer

```python
def _merge_results(
    old: dict[str, SandboxResult], new: dict[str, SandboxResult]
) -> dict[str, SandboxResult]:
    return {**old, **new}

class DiagnoseState(AppState):
    error_text: Annotated[str, _overwrite]
    broken_code: Annotated[str | None, _overwrite]
    error_signature: Annotated[ErrorSignature | None, _overwrite]
    sandbox_results: Annotated[dict[str, SandboxResult], _merge_results]
    last_verification: Annotated[SandboxResult | None, _overwrite]
    repair_attempts: Annotated[int, _overwrite]
    error_type: Annotated[str | None, _overwrite]
    explanation: Annotated[str, _overwrite]
    fixed_code: Annotated[str | None, _overwrite]
    change_summary: Annotated[list[str], _overwrite]
```

**不要重定义 `usage`**：`TypedDict` 子类不能把继承来的键换成不同的注解，`mypy --strict` 会红。
`usage` 继续是 `_overwrite`；每个 LLM 节点返回 `add_usage(当前值, 本次用量)`，
效果是累加，而 schema 没有分叉。

### D10 · 检索 query 由**确定性解析器**产生

`parse_traceback(error_text)` 抽出 `异常类 + 消息 + 最后一帧位置`，query 取
`f"{exception_type}: {message}"`（截断 200 字符）。不使用模型来改写 query：

- 前缀稳定、可复现，评估可重复；
- 不额外付一次模型调用；
- 模型仍有 `explain_error` 工具，可以在工具循环里换 query 再查。

空检索照旧 `raise RetrievalEmpty(query=query)`（S14）。

### D11 · 模型路由：诊断统一 `tier="pro"`

`AGENTS.md` §1：「强推理路由 `deepseek-v4-pro`……用于难诊断、代码修复」。

- `config.DIAGNOSE_MODEL_TIER: Final[Literal["pro"]] = "pro"`；
- 图构建时 `get_chat_model(tier=DIAGNOSE_MODEL_TIER)`；
- 模型名仍然只在 `config.py`（`§2` 单点所有权），图里只出现 `tier`。

成本提示：pro 的输入/输出单价约为 flash 的 4.4 / 3.3 倍（`config.PRICE_TABLE`）。
一次诊断的调用次数上限是 `MAX_TOOL_ROUNDS + MAX_REPAIR_ATTEMPTS + 1`；
跑分与批量任务安排在非峰值时段（§1「价格与错峰」、§10.5）。

### D12 · v2 不落库、不新增业务表

`AGENTS.md` §5.3 没有要求诊断历史；`/history` 是 v3/v4 的产物。
本轮诊断的完整结果通过 `data` 返回，用量通过 `meta.usage` 返回；
对话中间态只进检查点（§2「两份状态的分工」）。

**不要**为了"留痕"新建 `diagnoses` 表 —— 那会立刻制造第二个对话真相，
且 `tests/test_state_ownership.py:83-90` 的「业务表里不得有 messages」断言也会被迫改动。

### 5.2 `sandbox/runner.py`

```python

"""

def truncate_output(

    """返回 (截断后的文本, 是否截断, 截断前总行数)。纯函数，可离线测。"""

def sandbox_key(source: str, *, stdin: str = "", limits: SandboxLimits = SANDBOX_LIMITS) -> str: ...

class SandboxRunner(Protocol):

class DockerSandboxRunner:
    def __init__(self, *, client: DockerClient, image: str = SANDBOX_IMAGE, limits: SandboxLimits = SANDBOX_LIMITS) -> None: ...

    async def run(self, source, *, stdin="", timeout_seconds=None) -> SandboxResult:
        # 阻塞的 SDK 调用必须离开事件循环（AGENTS.md §3.4）
        return await asyncio.to_thread(self._run_sync, source, stdin, timeout_seconds)

def build_sandbox_runner() -> DockerSandboxRunner | None:
    """启动期探测：daemon 不可达 / 镜像不存在 → 返回 None（调用方降级并打日志）。"""

def probe_sandbox() -> tuple[bool, str | None]:
    """健康检查用的只读探测：能 ping 到 daemon 且镜像在位。"""
```

`_run_sync` 的执行顺序（**不可调换**）：

1. **拒绝线**：`source.strip()` 为空 → `rejected`（`reason="代码为空"`）；
   `len(source.encode()) > limits.max_code_bytes` → `rejected`（`reason="代码超过 N 字节"`）。
   不创建容器。
2. `containers.create(...)`，参数全部来自 `SANDBOX_LIMITS`：

   | 参数 | 值 | 对应契约 |
   |---|---|---|
   | `image` | `SANDBOX_IMAGE` | —— |
   | `command` | `["python", "-I", "-u", "-c", <引导脚本>]` | `-I` 隔离；真实入口是引导脚本，见第 3 步 |
   | `working_dir` | `"/work"` | —— |
   | `stdin_open` | `True` | 代码经 stdin 进来（U2 实测结论） |
   | `volumes` | **不设** | 不挂宿主路径（ADR 0004 决定 2 第 3 条） |
   | `network_disabled` | `not limits.is_network_enabled` | §5.3 无网络 |
   | `read_only` | `limits.is_rootfs_read_only` | §5.3 只读根文件系统 |
   | `mem_limit` / `memswap_limit` | `f"{memory_mb}m"` | §5.3 内存上限 |
   | `nano_cpus` | `int(cpus * 1_000_000_000)` | §5.3 CPU 上限 |
   | `pids_limit` | `limits.pids_limit` | fork 炸弹 |
   | `user` | `"10001:10001"` if `is_non_root` else 默认 | §5.3 非 root |
   | `cap_drop` | `["ALL"]` | 降权 |
   | `security_opt` | `["no-new-privileges:true"]` | 降权 |
   | `tmpfs` | `{"/tmp": f"rw,noexec,nosuid,size={tmpfs_size_mb}m"}` | 只读根文件系统下唯一可写处 |
   | `environment` | `HOME=/tmp`, `TMPDIR=/tmp`, `PYTHONDONTWRITEBYTECODE=1`, `PYTHONUNBUFFERED=1` | Python 需要可写 HOME |
   | `labels` | `{"pyassist.role": "sandbox"}` | 便于清理残留 |

3. `attach_socket(params={"stdin": 1, "stream": 1})`（**必须在 `start()` 之前**）。
4. `start()`，随即把 `长度头 + 源码 + 程序 stdin` 写进 stdin 流并 `shutdown(SHUT_WR)`：
   引导脚本靠 EOF 判断输入到头，落 `/tmp/main.py` 后 `execv`。写失败（`OSError`）视为
   沙箱故障 → `SandboxError`，不能误判成用户代码的 `status="error"`。
5. **轮询**：每 `SANDBOX_POLL_INTERVAL_SECONDS` 秒 `container.reload()`，
   读 `attrs["State"]["Status"]`；到截止时间仍未退出 → `kill()` → `status="timeout"`。
   这里**不调用** `container.wait(timeout=...)`：它抛的是 `requests.exceptions.ReadTimeout`，
   而 `requests` 不是声明依赖（§5.1 注释）。
6. 取输出：`logs(stdout=True, stderr=False)` 与 `logs(stdout=False, stderr=True)` **分两次**，
   分别解码（`errors="replace"`），再 `truncate_output`（D3）。
7. `finally`：`container.remove(force=True)`；移除失败只记日志，**不覆盖**主结果
   （但不得 `except: pass` —— 守护 #19）。
8. `status = "ok" if exit_code == 0 else "error"`（超时分支已单独返回）。

异常边界：

- `docker.errors.ImageNotFound` / `docker.errors.APIError` / `docker.errors.DockerException`
  → `raise SandboxError(f"沙箱不可用：{exc}")`（→500）。
- 用户代码的任何非零退出都**不进异常路径**。

### 5.4 `agent/tools/docs.py` 增量：`explain_error`

```python
@dataclass(frozen=True, slots=True)
class TraceFrame:
    file: str          # 只保留 basename，避免把宿主路径写进检查点与 prompt
    line: int | None
    function: str

@dataclass(frozen=True, slots=True)
class ErrorSignature:
    exception_type: str          # "AttributeError"；解析不出时为 "Unknown"
    message: str                 # ≤500 字符
    frames: tuple[TraceFrame, ...]   # ≤10 帧
    last_frame: TraceFrame | None  # 最外层调用点
    raw_tail: str                # ≤1000 字符，供 prompt 使用

def parse_traceback(error_text: str) -> ErrorSignature: ...

async def explain_error(
    error_text: str,
    *,
    top_k: Annotated[int, InjectedToolArg] = DEFAULT_TOP_K,
    start_index: Annotated[int, InjectedToolArg] = 1,
    searcher: Annotated[Searcher | None, InjectedToolArg] = None,
) -> tuple[str, list[RetrievedChunk]]: ...
```

`parse_traceback` 的规则（纯函数，离线可测）：

1. 从末尾往前找**最后一条**异常行 `异常类[: 消息]`（链式异常取最外层，即文件末尾那条）；
2. 帧用 `^\s*File "([^"]+)", line (\d+), in (.+)$` 收集，只保留 basename；
3. `SyntaxError` 的 `File "..."` 行没有 `in ...` 时，`function="<module>"`；
4. 全部匹配不到 → `exception_type="Unknown"`、`message=首行前 500 字符`；
5. 长度上限：`message ≤ 500`、`raw_tail ≤ 1000`、帧 ≤ 10 —— 检查点不是日志文件。

`explain_error` 的行为：

- query = `f"{exception_type}: {message}"[:200]`；空消息就只用类型名；
- `chunks = await searcher(query, top_k)`（无命中返回 `[]`，**不抛**）；
- 文本 = 错误类型 / 最后位置 / 错误消息 / `相关文档片段：` + `render_chunks(chunks, start_index=start_index)`；
- 返回 `(文本, chunks)`，artifact 与 `search_docs` **同形**（`list[RetrievedChunk]`），
  于是 `tools` 节点可以走同一条"追加 chunks → 重建 citations"的路。

工具描述（docstring）必须写清"它会解析报错并在官方文档里查找"，否则模型不会用。

### 5.14 评估：`errors.jsonl` / `metrics.py` / `run_v2_eval.py`

**数据集**（`src/pyassist/evals/datasets/errors.jsonl`，20 条，**只增不改**）：

```json
{"id":"attribute-01","topic":"AttributeError","error_text":"Traceback (most recent call last):\n  File \"...\", line 1, in <module>\n    'abc'.push('d')\nAttributeError: 'str' object has no attribute 'push'","broken_code":"s = 'abc'\ns.push('d')","expected_error_type":"AttributeError"}
```

字段集合**恰好**：`{"id","topic","error_text","broken_code","expected_error_type"}`。

**采集方式**：用本机 Python 3.12 真实运行坏代码、把 stderr 原样贴进 `error_text`
（不是手写 traceback）。手写的 traceback 与真实格式（缩进、`^^^^` 指示、链式异常）
有差异，会让 `parse_traceback` 的准确率失真。

覆盖的 20 个类型（每类 1–2 条，全部是初学者真实会遇到的）：

`AttributeError`、`TypeError`、`NameError`、`KeyError`、`IndexError`、`ValueError`、
`ZeroDivisionError`、`UnboundLocalError`、`ImportError`/`ModuleNotFoundError`、
`IndentationError`、`SyntaxError`、`FileNotFoundError`、`RecursionError`、
`json.JSONDecodeError`、`UnicodeDecodeError`、`asyncio.TimeoutError`/`RuntimeError`、
`StopIteration`、`OSError`、`PermissionError`、`OverflowError`。

**`evals/metrics.py` 增量（纯函数）**：

```python
def error_type_accuracy(predicted: Sequence[str | None], expected: Sequence[str]) -> float: ...
def fix_pass_rate(statuses: Sequence[str]) -> float: ...   # status == "ok" 的比例
```

- 两者都要求等长、非空；空输入返回 `0.0` 而不是抛异常（与 `recall_at_k` 的口径一致）。
- 不引入 LLM 裁判：错误类型是**可判定**的字符串比较；修复是否通过由沙箱退出码决定。

**`evals/run_v2_eval.py`**：

- 结构与 `run_rag_eval.py` 一致：`_Row` / `run()` / `_evaluate_record()` / `_load_records()` / `_report()` / `_main()`；
- `run()` 构一张真实诊断图（pro + Docker runner + 真实检索 + 临时 SQLite 检查点）；
- 每条：`run_diagnosis` → 收集 `error_type` 与 `verification.status`；
- `AppError` 记为该行失败，不中断全量；
- 输出一行：`records=20 error_type_accuracy=0.xx fix_pass_rate=0.xx timeouts=n`；
- CLI：`--limit`、`--dataset`（默认 `ERRORS_DATASET_PATH`）；
- **不进 CI**：需要真实 Docker 与 API key；安排在非峰值时段（§1「价格与错峰」）。

### 5.15 `tests/fakes/sandbox.py` + `tests/fakes/llm.py` 增量

`FakeSandboxRunner`：

```python
class FakeSandboxRunner:
    """脚本化沙箱。**绝不执行任何代码**（连 compile 都不做）。"""

    def __init__(self, results: Sequence[SandboxResult] | None = None) -> None:
        self.script = list(results or [])
        self.calls: list[str] = []

    async def run(self, source, *, stdin="", timeout_seconds=None) -> SandboxResult:
        self.calls.append(source)
        if not self.script:
            raise AssertionError("FakeSandboxRunner 脚本已耗尽")
        return self.script.pop(0)
```

辅助 `result(status="ok", stdout="", stderr="", exit_code=0)` 构造 `SandboxResult`，
`idempotency_key` 用生产同款 `sandbox_key` 生成，保证图里的缓存键一致。

`ScriptedChatModel` 增补：

```python
structured_script: list[BaseModel] = []
structured_requests: list[list[BaseMessage]] = []

def with_structured_output(self, schema, *, include_raw=False, **kwargs):
    return RunnableLambda(self._structured_step)   # 弹出 structured_script，按 include_raw 返回
```

- `include_raw=False` → 直接返回 pydantic 实例；
- `include_raw=True` → `{"raw": AIMessage(...), "parsed": obj, "parsing_error": None}`，
  其中 `raw` 带 `usage_metadata`，用来断言 pro 档用量被记账。
- 这是**测试基建**，`src/` 不知道它存在（同 `tests/fakes/__init__.py` 的约定）。

`conftest.py` 增量：

- `fake_sandbox()`：空的 `FakeSandboxRunner`；
- `diagnose_app(...)`：`create_app(..., diagnose_model=scripted_model, sandbox_runner=fake_sandbox,
  search/fetch/preflight=...)`，与 `qa_app` 共用检索闭包；

## 9. 与 ROADMAP / 阶段六的差异（均需知悉）

1. **`explain_error` 落在 `agent/tools/docs.py`**（ROADMAP 未指定文件）。

   必须与"api 容器本身只跑我们的代码"这一前提绑定）。推荐：阶段八再定，本阶段只在
   `docs/evals/阶段七-跑分.md` 里记录本地前提。
2. **`timeout_seconds` 是否校准**：现在是 10s。推荐：T0/U6 实测一次"`import json` + 空脚本"
   的冷启动耗时，若 > 2s 就把上限提到 15s；**校准前不要声称 10s 已验证**（§2.3）。
3. **`SandboxTimeout` / `SandboxRejected` 是否要抛**：推荐**不抛**，统一用
   `SandboxResult.status`。两个异常类保留（§3.2 已登记，删掉是破坏性变更），
   §11 记录它们的语义仍由 `data.status` 承载。
4. **`/health` 是否暴露 `sandbox_ok`**：推荐**本阶段不加字段**。`HealthData` 在
   `api/schemas.py`（契约冻结），新增字段虽属追加，但没有消费方；先用
   `status="degraded"` + 启动日志表达，阶段八随部署一起增补。
5. **pro 档成本**：一次诊断最多 `3 轮工具 + 2 次修复 + 1 次首答 = 6` 次模型调用；
   以 `PRICE_TABLE` 粗算，单次在**美分级**。推荐跑分排在非峰值时段（UTC 周一至周五
   01:00–04:00 与 06:00–10:00 之外）。
6. **启动时是否做模型名校验**：阶段二只提供手动 CLI（`python -m pyassist.llm.client --check-models`）。
   推荐本阶段**不改**启动路径；T0 手动跑一次，把结果写进跑分文档。
7. **诊断是否落库**：推荐**不落**（D12）。v3 有 `exercise_attempts` / `mistakes` 时才归档，
   那时由 `record_*` 的 `idempotency_key` 唯一约束兜底。
8. **`MAX_REPAIR_ATTEMPTS` 取 2 是否够**：推荐先跑 20 条评估，看"第二次修复才通过"的比例；
   若 > 20%，把它提到 3 并在跑分文档里记录成本变化。**不要为了提分无限重试**。
9. **镜像 tag 版本策略**：`pyassist-sandbox:1` 固定；Dockerfile 一改就 bump 到 `:2`。
   推荐不引入 `:latest` —— runner 不自动拉取，`:latest` 只会让"跑的是哪个镜像"变成谜。
10. **`errors.jsonl` 的 20 条如何挑选**：推荐按"初学者真实报错"分布，而不是按异常类均匀分配；
   每条都要有可直接复现的 `broken_code`。禁止为了跑分好看挑简单样例（§4 的评估集纪律）。
