## 决定 1 · §3.2 增补四个传输层错误码【已批准 2026-10-03】

### 背景

`AGENTS.md` §3.1 规定 `error.code` **只能取 §3.2 的枚举，不得自造字符串**；
而 §3.2 的异常树全部是**业务**异常。有四种失败根本不经过业务代码：

| 情形 | 谁抛的 |
|---|---|
| 404 未知路由 | starlette 在路由匹配阶段 |
| 405 方法不匹配 | starlette 在路由匹配阶段 |
| 429 本服务限流 | slowapi 的中间件 |
| 500 未分类异常 | 兜底处理器 |

它们无码可取。若不解决，§3.1 的"任何失败都带完整信封"与"`error.code` 只取枚举"
这两条**无法同时满足** —— 阶段四的验收判据 6 因此不可达。

### 结论

在 §3.2 增补四个与业务树**同级**的传输层码，并已在 `AGENTS.md` §3.2 落地：

```
NOT_FOUND             → 404（未知路由）
METHOD_NOT_ALLOWED    → 405（方法不匹配）
RATE_LIMITED          → 429（本服务对调用方限流，slowapi）
INTERNAL_ERROR        → 500（兜底：未分类异常）
```

### 理由

- **是"新增"不是"改语义"**：既有 12 个码的状态码、`ok` 标志、含义一律未动，
  树的结构也未动。新增是纯粹的超集操作。
- **发生在首次发布之前**：`API_VERSION` 尚未发布（无已发布契约、无 `frontend/` 消费方），
  故不触发 §6 的破坏性变更流程（bump `API_VERSION` + 同步 `frontend/`）。
  增补之后，这四个码与树内各码受**同样的**冻结约束。
- **`RATE_LIMITED` 必须与 `LLMRateLimited` 分开**：状态码同为 429，但语义相反 ——
  前者是**我们**限调用方（对方该退避），后者是**上游**限我们（我们该退避）。
  合并会让"谁被限流了"在成本/可用性报表里消失。这是本决定里最容易做错的一处。

### 影响

- `src/pyassist/errors.py` 的 `ErrorCode` 由 12 个成员变为 16 个。
- `src/pyassist/api/errors.py` 增加三条传输层处理器（`StarletteHTTPException` /
  `RateLimitExceeded` / 兜底 `Exception`），详见阶段四 SPEC §4.3。
- 判定"新错误码是否合法"的规则不变：**取值的完整集合 = 业务树叶子码 + 这四个**。

## 决定 2 · 保留唯一的兜底 `Exception` 处理器

### 背景

§3.2 的处理原则写着"**捕获链条，不要捕获大类**……禁止一个 `except Exception` 吞掉全部"；
而 §3.1 要求**任何**失败都带完整信封，FastAPI 对未捕获异常默认返回 `{"detail": ...}`。
两条要求在 500 这一格上正面冲突。

### 结论

保留**唯一一处** `except Exception`（`api/errors.py` 的 `_handle_unexpected`），
并用三条边界把它与"吞异常"区分开：

1. **不外泄**：响应的 `message` 是固定文案，绝不拼接 `str(exc)` 或 traceback；
   日志里也只记 `error_type`，不记 message（可能含用户代码）。密钥更不得进任何一处。
2. **有打点**：必须 `structlog` 打点并带 `request_id`（显式传参 —— 走到兜底时
   contextvars 已被清理，见 SPEC §1.5 的 M5）。
3. **不吞语义**：函数体是"构造信封 + 打点 + 返回"，不是 `pass` / `...`；
   `except Exception: pass` 由守护 #19 在 CI 拦截。
   异常仍然以 500 如实上报，只是穿上了信封。

### 理由

信封完备性压倒局部洁癖：§3.1 是全项目对外的唯一承诺，存在一条漏出 `{"detail": ...}`
的出口就足以让前端的分支判断失效。而 §3.2 那句禁令的真实目标是**不要吞掉异常、
不要把不同故障混成一类** —— 边界 1–3 恰好保住了这两点。

### 影响

阶段四之后，`grep -rn "except Exception" src/` 应当只命中两处，且两处都有函数体：
`api/errors.py` 的 `_handle_unexpected` 与 `api/main.py` 里 `/health` 的探活 try
（探活的全部意义就是"连不上也要给出信封"）。

## 决定 3 · 三个"正常结果"用 `ok: true` 的 200 信封

### 背景

§3.2 有三个异常映射到 **200**：`RetrievalEmpty` / `SandboxTimeout` / `SandboxRejected`。
它们的共同点是"**这是业务结果，不是故障**"：文档里没有答案、用户代码超时、用户代码被
安全边界拦截，都属于实验/问答的正常产物。

### 结论

由**异常处理器**把这三种异常转成 `ok: true` 的 200 信封，`data` 取异常自带的载荷
（`data.status ∈ {"empty","timeout","rejected"}`）。

映射表因此不只承载状态码，还要承载 `ok` 标志（`_Mapping(status, ok)`）。

### 理由

保住"`api/errors.py` 是唯一异常映射点"这条 §4 禁区。服务层只负责 `raise`，
不理解 HTTP —— 若改成"服务层直接返回状态值"，HTTP 语义就渗进了领域层，
且会出现第二条"决定响应长什么样"的代码路径。

### 影响

- `AppError` 需要两个语义不同的槽：`data`（只喂成功信封，仅这三个异常使用）与
  `details`（只喂 `error.details`）。合二为一会让"这个异常是失败还是正常结果"
  变成运行时才可判定的事。
- 阶段四 SPEC §4.9 对这三条**单独**断言 `== 200`，防止有人"顺手统一成 5xx"。

## 决定 4 · `cost_usd` 显式序列化为 float

### 背景

实测 pydantic 2.13.5：`Usage(cost_usd=Decimal("0.0004")).model_dump(mode="json")`
得到 `{"cost_usd": "0.0004"}` —— **带引号的字符串**。而 §3.1 的契约示例是数字 `0.0004`。

### 结论

在 `api/schemas.py` 的 `Usage.cost_usd` 上挂 `@field_serializer`，
返回 `round(float(value), 8)`；并保证所有出口都用 `model_dump(mode="json")`
（用默认的 python mode 不会走 JSON 序列化路径）。

### 理由

- 类型契约要按**示例**对齐：前端拿到字符串会直接进 `toFixed` 之类的数值运算而静默出错。
- `round(..., 8)` 而非裸 `float(...)`：金额由 `Decimal` 运算得到，
  直接转 float 会带二进制尾巴（形如 `0.0004000000000000001`），
  既污染契约快照，也会让"只比字段名"的测试意图被绕过。

### 影响

契约快照 `tests/snapshots/envelope.json` 只冻结**字段名**、不冻结取值 ——
正因为 float 的格式化细节对比较敏感，快照比取值会变成 flaky 之源。
取值层面的保证由 `test_usage_serializes_whole_numbers` 单独断言。

## 决定 5 · 修正 §3.1 的失败示例（补零值 `usage`）【已批准 2026-10-03】

### 背景

`AGENTS.md` §3.1 的**规则**写着"`meta` 三个字段**永远存在**，即使出错。缺 `usage` 时
填零值而非省略"，但同一节的**失败示例**里 `meta` 只有 `request_id` 与 `latency_ms` ——
示例与规则自相矛盾。实现时按哪一条都能自圆其说，这正是最坏的一种不一致。

### 结论

**按规则改示例**：失败示例补上零值 `usage`（`prompt_tokens` / `completion_tokens` /
`cached_tokens` 为 0，`cost_usd` 为 `0.0`，`is_off_peak` 为 `true`），并就地注明"缺就填零、
不省略字段"。

### 理由

- **规则是对的，示例是笔误**。`usage` 永远在位，前端才能无条件读
  `meta.usage.cached_tokens`（成本报表的关键字段），不必写 `?.` 分支 ——
  契约的价值恰恰在于"消费方不需要防御性编程"。
- **反方向（改规则为"失败时可省 `usage`"）代价更大**：那是**改 §3.1 语义**，
  属 §6 的破坏性变更，需 bump `API_VERSION` 并同步 `frontend/`。为一个笔误付这个代价不值。
- 本次是**文档修正**，不是语义变更 —— 既有消费方拿到的响应 `usage` 一直是零值
  （阶段四之前根本没有 API），故不涉及 `API_VERSION`。

### 影响

- 阶段四 SPEC §4.8 的 `test_meta_always_carries_usage` 断言的正是这条规则，
  它同时锁住了"示例与规则一致"这件事不会再退化。
- §3.2 里那条 `RetrievalEmpty → 200` 的示例（`error.code` 用 `RETRIEVAL_EMPTY`）
  不受影响。

## 施工中发现 · `include_router` 让 slowapi 的默认限流静默失效（阶段四 T6）

**不是取舍，是实测缺陷，记此以免阶段六重蹈。**

### 现象

SPEC §1.4 只核对了 slowapi 的挂载三步与"异步处理器会被丢弃"（M6），未验证**默认限流是否真的
生效**。实测（本机 fastapi 0.142.2 + starlette 1.7.0 + slowapi 0.1.10）：

- fastapi 0.142 的 `include_router` 不再把子路由摊平进 `app.routes`，而是塞进一个
  `_IncludedRouter` 包装对象；
- 该对象 `matches(scope)` 会返回 `Match.FULL`，但**没有 `.endpoint` 属性**；
- slowapi 的 `_find_route_handler` 只认 `Match.FULL and hasattr(route, "endpoint")`，
  故取到 `None` → `_should_exempt` 返回 `True` → **整条默认限流被跳过**。

结果是：`/health` 打多少次都返回 200，`DEFAULT_RATE_LIMIT` 形同虚设，且**不报错**。

### 结论

`create_app` 的路由挂载由 `app.include_router(_health_router)` 改为
`app.router.routes.extend(_health_router.routes)`（0.142 之前 `include_router` 的等价行为）：
路由可达、进 OpenAPI、且 slowapi 能看到 `.endpoint`。

### 影响

- `tests/test_envelope.py::test_rate_limited_end_to_end` 同时钉住三件事：429 走我们的信封、
  `/health` 进 OpenAPI、默认限流真的生效。任何人换回 `include_router` 会立刻红。
- **阶段六新增业务 router 时必须沿用同一挂载方式**（或改用 `@limiter.limit(...)` 装饰具体端点，
  那条路径不依赖 `_find_route_handler`，另有其要遵守的约束）。这条是阶段六的必读项。
- 这是**实现层**的修正，不改变任何一条 §3.1 / §3.2 契约，故不涉及 `API_VERSION`。
