# 阶段六跑分：v1 文档问答（Recall@5 + 引用准确率）

本文件记录**手动跑分的方法与结果**。跑分不进 CI —— 它要真实索引、真实
`DEEPSEEK_API_KEY` 和网络，而 `AGENTS.md` §5.1 要求测试全部离线。
进 CI 的是**算术本身**：`evals/metrics.py` 是纯函数，由 `tests/test_rag_eval.py`
用固定假数据钉死（含边界：`k` 超长、重复 URL、零标记、越界标记）。

---

## 1. 跑分前的前置条件

| 条件 | 检查方式 | 不满足时的表现 |
|------|----------|----------------|
| 语料已 ingest（`data/chroma/` 有索引） | `python -c "from pyassist.rag.retriever import probe_index_depth; ..."`，或直接看 `data/chroma/` 是否非空 | 命令以退出码 2 结束，stderr 打印"跑分无法开始：…"，`CorpusMissing` |
| `DEEPSEEK_API_KEY` 已配置 | `.env` 或环境变量 | 同上，`ConfigError` |
| 网络可达 `api.deepseek.com` | `curl https://api.deepseek.com/models` | 每条记录记失败，`failed_records` 等于总数 |
| 处于**非峰值时段** | 见 §4 | 能跑通，但单价翻倍 |

> **不要**用 `count()` 判断索引可用（`AGENTS.md` §4）。元数据段和 HNSW 会撕裂：
> 实测坏库 `count()` 报 17366、检索只找得到 983 条。要判可用性用
> `rag/retriever.py::probe_index_depth`。

---

## 2. 怎么跑

```bash
# 全量（44 条），Recall@5
python -m pyassist.evals.run_rag_eval

# 冒烟：先跑 3 条确认链路通，再跑全量
python -m pyassist.evals.run_rag_eval --limit 3

# 换 k 值（例如看 Recall@10 的上限在哪）
python -m pyassist.evals.run_rag_eval --k 10
```

每条记录做两件事：

1. `retriever.retrieve(question, top_k=k)` → 算 Recall@k（**不调模型**）；
2. 跑一遍完整的 QA 图（可能多轮工具调用）→ 从答案里数 `[n]` 标记 → 算引用准确率。

开销量级：44 条 × 1 次图运行。Flash 档、非峰值时段是**美分级**成本，不是问题；
真正的约束是"别在峰值跑"和"别在调试循环里反复跑全量"。

## 3. 输出与判定

唯一输出行（`run_rag_eval.py::_report` 打印的就是它，`tests/test_rag_eval.py` 逐字断言）：

```
records=44  recall@5=0.8xx  citation_accuracy=0.9xx  answers_without_citation=0
```

有失败记录时追加一行：

```
failed_records=3（按 0 计入上面的均值，明细见日志）
```

判定门槛（`AGENTS.md` §5.2）：

| 指标 | 门槛 | 含义 |
|------|------|------|
| `recall@5` | ≥ 0.80 | top-5 命中的相关页数 / 该题相关页总数（按 `doc_url` 去重） |
| `citation_accuracy` | ≥ 0.90 | 答案中每个 `[n]` 指向的 `doc_url` 属于该题 `relevant_urls` 的比例 |
| `answers_without_citation` | = 0 | 实质性回答必须至少带 1 个可点击来源 |

三条读法上的约定：

- **分母永远是全部用例**。失败、空检索都按 0 计入均值 —— 否则"跑挂一半"会表现为分数变高。
- **零标记记 0.0，不是 1.0**。不能奖励"什么都不溯源"。
- **越界标记 `[9]` 记 0 分**。读者点不到它，与"引用错了"等价。

### 指标是代理，不是语义裁判

`citation_accuracy` 的完整定义是"链接指向的文档**确实包含**支撑该结论的片段"，
那需要语义判断。本阶段用"链接指向的文档是否属于该题的相关文档集"近似
（SPEC §10.3）。取舍很明确：**完全可复现、零成本、可进 CI**，代价是它测的是
"指向对不对"，不是"支撑不支撑"。要加 LLM 裁判，做成 `experiments/` 下的独立脚本，
不要进 `evals/metrics.py` —— 那会让分数依赖一次模型调用的随机性。

## 4. 错峰（最大的一笔免费节省）

峰值时段（UTC）：**周一至周五 01:00–04:00 与 06:00–10:00**，其余时段半价。
换算成本地时间再排期，别照着 UTC 猜。批量任务（本跑分、re-ingest）都应落在非峰值。

## 5. 结果记录

每次跑完把这一行抄进下表。**没有真实索引与 key 的环境不产生分数**，
因此下面当前只有方法、没有数字 —— 不要凭测试里的假数据填表。

| 日期（UTC） | 是否峰值 | 命令 | 输出行 |
|-------------|----------|------|--------|
| 待填 | 待填 | `python -m pyassist.evals.run_rag_eval` | 待填 |

记录时同时写下当次的：

- `config.RETRIEVAL_MIN_SCORE` 值（当前 `0.0`，不过滤）；
- embedding 模型与 `config.HNSW_SYNC_THRESHOLD` / `HNSW_BATCH_SIZE`（重建索引后分数不可比）；
- 数据集版本（`src/pyassist/evals/datasets/qa.jsonl` 的 git commit）——
  评估集**只能新增、禁止修改**（`AGENTS.md` §4），跨版本比较前先确认这一点。

---

## 6. 低于门槛时先看什么

按顺序排查，**不要**一上来调阈值：

1. **`retrieval.done` 日志里的 top-5 分数分布**。若相关页根本没进 top-5，是召回问题；
   进了 top-5 但排名靠后，是排序问题。
2. **语料覆盖**。问题问的章节是否真的 ingest 了？`data/corpus/**` 禁止手改，
   要补只能跑 ingest 的抓取流程。
3. **embedding 是否前后一致**。ingest 与检索必须是同一个 `rag/embedder.py` 出口；
   换过模型而没重建索引，向量空间对不上，检索会退化成噪声。
4. **最后才考虑 `RETRIEVAL_MIN_SCORE`**。调高阈值会先压低 Recall@5 ——
   两个指标互相拉扯，必须一起看（SPEC §10.2）。
