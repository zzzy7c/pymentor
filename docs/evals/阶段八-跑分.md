# 阶段八跑分：v3 练习生成 + 批改、v4 推荐

本文件记录 **v3/v4 的跑分方法、门槛与结果**。和阶段六、阶段七同一纪律：
真实跑分要 Docker（`pyassist-sandbox:1`）、真实 `DEEPSEEK_API_KEY`、已建好的向量索引
和网络，**不进默认 CI**；进 CI 的是算术本身与数据集结构。

> **当前状态（2026-10-25）：夹具自洽与生成自洽都产生了真实分数（均 `1.000`，见 §5）。**
> 仍待跑的是标注导出与评分一致率（后者依赖人工标注）；`-m docker` 的隔离用例已全部通过
> （见 §7 第 3 条）。未跑的部分不是 0，也不是"看起来应该没问题" —— 在真的跑通并记录之前，
> §1 对应的门槛**不能声称已验证**。

## 1. 门槛

| 指标 | 门槛 | 依据 | 谁来测 |
|------|------|------|--------|
| 夹具自洽率 `self_consistency` | **1.000** | `AGENTS.md` §5.4：每道题的参考答案必须能让自己的测试全绿 | `--self-consistency`（需 Docker，不需要模型） |

## 2. 跑分前的前置条件

| 条件 | 检查方式 | 不满足时的表现 |
|------|----------|----------------|
| Docker daemon 已启动 | `docker info` | `--self-consistency` / `--generate` 以**退出码 2** 结束，stderr 打印"缺少依赖：需要 Docker daemon 与 pyassist-sandbox:1 镜像" |
| 沙箱镜像存在 | `docker image ls pyassist-sandbox` | 同上（`build_sandbox_runner()` 返回 `None`） |
| 语料已 ingest | `rag/retriever.py::probe_index_depth`（**不要**用 `count()`，§4） | 生成图的检索降级；生成质量可能下降，不中断 |
| `DEEPSEEK_API_KEY` 已配置 | `.env` 或环境变量 | `--generate` 退出码 2（`ConfigError`）；其余三种模式不需要模型 |
| 网络可达 `api.deepseek.com` | `curl https://api.deepseek.com/models` | `--generate` 每条记失败，`self_consistency` 变低 |
| 处于非峰值时段 | 见 `AGENTS.md` §1 | 能跑通，但 pro 档单价翻倍 |
| 有历史提交（仅 `--export-labels`；建议 ≥ 30 条，少于 30 也能导出） | `GET /history` 或直接查 `exercise_attempts` | stderr 提示"没有可导出的提交"，退出码 2 |

`--export-labels` 与 `--agreement` **不需要 Docker 和模型**：前者只读业务库与检查点，
后者只做整数比较。

## 3. 怎么跑

```bash
# 1) 夹具自洽（需 Docker，不调模型）
uv run python -m pyassist.evals.run_v3_eval --self-consistency

# 2) 真实生成 + 自校验（需 key + Docker；默认每主题 5 道 = 20 道）
uv run python -m pyassist.evals.run_v3_eval --generate --per-topic 5

# 3) 导出最近 30 条提交为空白标注 CSV（写在 docs/evals/，已被 .gitignore 排除）
uv run python -m pyassist.evals.run_v3_eval --export-labels 30

# 4) 人工填完 human_score 后计算一致率
uv run python -m pyassist.evals.run_v3_eval --agreement docs/evals/阶段八-标注样本-2026-10-22.csv
```

四种模式互斥，必须给且只给一个（argparse 的 mutually exclusive group）。

### 输出行

| 模式 | 唯一输出行 |
|------|-----------|
| `--self-consistency` | `records=8 self_consistency=1.000 timeouts=n` |
| `--generate` | `records=20 self_consistency=0.xxx failed=n` |
| `--export-labels` | `samples=N path=docs/evals/阶段八-标注样本-<日期>.csv` |
| `--agreement` | `samples=30 agreement=0.xxx` |

- **分母永远是全部用例**：生成失败、超时、解析失败都按 `False` 计入，不从中删掉。
- `timeouts` 单独计数：沙箱超时是实验结果（`data.status="timeout"`），不是服务故障。
- 缺 Docker / key / 输入统一**退出码 2**，不打印 0 分 —— "跑不起来"不是跑分结果。
- 生成模式走**生产图**（`build_exercise_graph(checkpointer=None, ...)`），不重写一遍
  自校验循环。每条用独立 thread id（`eval-v3-<run_id>-<topic>-<n>`），不碰业务表。

### 标注 CSV 的字段

```
sample_id, prompt, submitted_code, test_summary, model_score, human_score
```

`human_score` 导出时为空，由人填 0–100。文件编码是 `utf-8-sig`（Excel 打开中文不乱码），
**含用户提交代码，不进 git**（`.gitignore` 已有 `docs/evals/阶段八-标注样本-*.csv`）。

## 4. 评估集从哪来

`src/pyassist/evals/datasets/exercises.jsonl`：8 条，四个主题各 2 条
（列表 / 字典 / 装饰器 / 异步），字段恰好是
`{id, topic, title, prompt, starter_code, reference_solution, tests}`。

- **人工编写**，不是模型生成后直接入集：生成入集会让评估集随模型漂移，
  下次跑分就不再是同一把尺子。
- 测试只用 `unittest` 与标准库；每题 3 个测试方法。
- 已做的本地校验：8 条参考答案分别用 `python -I` 在临时目录跑自己的测试，均 **3/3 通过**。
  这只是**参考实现本身**的检查，**不替代**沙箱自洽跑分 —— 容器里的解释器、用户、
  只读根文件系统与 10s 超时都可能改变结果。
- **只能新增，禁止修改已有用例**（`AGENTS.md` §4）。`tests/test_exercise_eval.py`
  盯住条数、每主题 2 条、字段集合、id 唯一与 topic 取值。
- `run_v3_eval._load_records` 校验字段集合**恰好相等**：多一个少一个都拒绝跑分。

## 6. 低于门槛时先看什么

按顺序排查，**不要**一上来改阈值、改评估集或改 `metrics.py`：

1. **整批失败**：看 `eval.v3.generate_failed` / `eval.v3.self_consistency` 日志的
   `error` / `status`。全是 `ConfigError` 是环境问题；全是 `timeout` 先看 §7 第 1 条。
2. **夹具自洽不是 1.000**：这是**题目坏了**，不是模型问题。逐条看
   `parse_test_report` 的失败用例名，先把参考答案或测试改对；
   但评估集"禁止修改已有用例"—— 正确做法是新增一条修正用例并在变更说明里留痕。
3. **生成自洽低**：先看 `generation_attempts`。达到 `MAX_EXERCISE_ATTEMPTS=2`
   仍不过说明模型出题质量不够，可以按 SPEC §10 的建议临时换档，但必须在本文记录；
   不要为了提高分数放宽 `self_check`。
4. **一致率低**：看模型分数与人工分数差在哪个方向。若系统性地高 20 分以上，
   是评分 prompt 的锚点问题；若散乱，是样本太少（30 份是下限，不是充分条件）。
5. **禁止**挑选简单题目、修改已有标注、改 `grading_agreement` 的容差来提分 ——
   这是本项目最严重的作弊（`AGENTS.md` §4、SPEC §4）。

## 7. 待定项与未验证项

1. **测试执行的超时未校准**（SPEC U4）。练习测试复用 `SandboxLimits.timeout_seconds=10`，
   没有单独的 `test_timeout_seconds`。`python:3.12-slim` 冷启动 + 若干 `unittest`
   是否稳定落在 10s 内，必须实测；若频繁 `timeout`，再在 `SandboxLimits` 增
   `test_timeout_seconds=15`（改 `config.py` 与 `sandbox/runner.py`，走评审）。
   现有证据只是"够用"：夹具自洽 8 条、生成自洽 20 条与 `-m docker` 全部用例都在 10s 内
   跑完（`timeouts=0` / `failed=0`），但这不是冷启动耗时的校准数据。
2. **四种模式中夹具自洽与生成自洽已有真实分数（2026-10-25，均 `1.000`）。**
   仍待跑：`--export-labels` 与 `--agreement`，后者依赖人工标注 30 份样本。
3. **`-m docker` 的 11 条用例已运行并通过（2026-10-25）。**
   `uv run pytest -m docker -v` → `11 passed, 434 deselected`。其中 10 条是安全边界
   （无网络、只读根文件系统、非 root、fork 炸弹、`rm -rf /`、读 `/etc/passwd`、
   容器不泄漏等），1 条是 `test_exercise_self_consistency.py`（8 条夹具的参考答案
   过自身测试）。SPEC §5.3 的沙箱验收与 §5.4 的"100% 自洽"因此**均已由真实执行
   验证**；后者与 §5 的 `--self-consistency` 分数互为旁证。
4. **评分一致率需要人。** `--export-labels` 只导出；30 份标注与 `--agreement`
   必须由人完成，机器不能代替。
5. **v4 推荐没有数值跑分。** SPEC §5.5 的判据是"引用该用户实际做错的题目 id"，
   由 `graphs/progress.py::finalize` 剥离非法 id + `tests/test_progress_graph.py`
   离线保证；"推荐好不好"属于主观评价，本阶段不设自动指标。
6. **生成模型档只跑过 `pro` 一组，没有对比数据。** `--generate` 已产出
   `self_consistency=1.000`（`EXERCISE_MODEL_TIER=pro`）；若要用 `flash` 降本，
   必须重跑同一命令并把两组数字都写进 §5 —— 只降档不记录，等于放弃可比性。

**判定口径**（一条不合格就写"未通过"并记下 code，不要写"看起来没问题"）：

- 任一步出现红色 `CODE：message` → 该步失败，记下 code（如 `RETRIEVAL_EMPTY`、`SANDBOX_TIMEOUT`、
  `LLM_RATE_LIMITED`）。若 `RETRIEVAL_EMPTY` 确因语料里没有该主题，算"正常作答"、不算失败，但要写明。
- 诊断页出现「本次没有沙箱验证结果」→ 记"**未验证**"，不算通过（`sandbox_ok` 在这次请求里丢了）。
- 推荐的 `exercise_ids` 为空、或含你没做错过的题 → 失败（产品原则：宁可说"还不够"，也不编造）。
- 统计页 token 非零而「今日成本」为 `$0.000000` → 记账断了，记失败（问题在 `llm/tracing.py`）。
