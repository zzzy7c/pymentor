# ADR 0001 · 模型名校验真机结论（阶段二 T8）

- 日期：2026-10-03
- 状态：**已记录，待人工拍板**（本 ADR 不改变任何代码行为）
- 触发：SPEC 阶段二 §5「人工步骤」+ 待定项 3 / 待定项 6 要求把 `--check-models` 的结论落到 ADR

## 命令

```bash
uv run python -m pyassist.llm.client --check-models
```

## 实测结果

| 项 | 结果 |
|---|---|
| 端点可用性 | ✅ `https://api.deepseek.com`（**不带 `/v1`**）可用，`models.list()` 正常返回 |
| 退出码 | **1**（不一致）—— 按 SPEC §5.3，**不计入阶段二验收失败** |
| `config.EXPECTED_MODEL_IDS` | `deepseek-v4-flash`、`deepseek-v4-pro` |
| 实机 `available` | `deepseek-flash`、`deepseek-v4-pro` |
| 缺失 | `deepseek-v4-flash` |

## 结论

1. **端点可用，待定项 6 关闭。** `config.DEEPSEEK_API_BASE_URL = "https://api.deepseek.com"`（不带 `/v1`）
   实测不是 404，无需改成带 `/v1` 的形式。`client.py` 显式传 `base_url` 覆盖库默认值的做法保持。
2. **模型名漂移属实，且方向与 SPEC §1 的预测一致。** SPEC §1 原话：定价页写的是
   `deepseek-flash`，`deepseek-v4-flash` 是仍在被路由的旧名。实机 `models.list()` 只列
   `deepseek-flash`，**不列** `deepseek-v4-flash` —— 这正是"只告警不阻断"要防的情形：
   若把它做成硬失败，一次上游改名就会打挂整个应用与部署。
3. **`check_models()` 的行为符合设计**，无需改动：`is_ok=False`、`missing={deepseek-v4-flash}`、
   `error=None`（不是网络/鉴权失败），结果存进 `client.get_last_model_check()`，供阶段四的 `/health` 读。

## 待人工拍板（阻塞阶段六的第一张图，不阻塞阶段二）

`config.MODEL_FLASH` 目前是 `deepseek-v4-flash`，而实机清单只列 `deepseek-flash`。
`models.list()` 是**商品目录**，不等于**路由能力** —— 旧名可能仍被路由，也可能已被弃用。

- **选项 A（不改）**：保留 `deepseek-v4-flash`。若旧名仍在被路由，阶段六的图能直接跑；
  风险是若已弃用，第一次真实调用才会暴露 `LLMModelNotFound`（§3.2 已登记该错误码，映射 500）。
- **选项 B（改成 `deepseek-flash`）**：与实机清单一致。改动只在 `config.py` 一处（§1 / §2），
  但会改变所有 tier="flash" 的调用所命中的模型，属于需要人工确认的产品决定。
- **需要一次真实 chat 调用才能定论**：`models.list()` 测不出来，只能用一次最小
  `chat.completions.create` 试 `deepseek-v4-flash` 是否 200。本次未执行（超出 SPEC 授权的人工步骤范围）。

**推荐**：阶段六开工前跑一次最小真实调用定论，把结果并进本 ADR；在那之前保持选项 A 不动。
