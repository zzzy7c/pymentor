# 阶段七跑分：v2 错误诊断（错误类型准确率 + 修复通过率）

本文件记录 **v2 的手动跑分方法、真实隔离验收方法与结果**。跑分不进 CI ——
它要真实 Docker（`pyassist-sandbox:1` 镜像）、真实 `DEEPSEEK_API_KEY`、已建好的
向量索引和网络，而 `AGENTS.md` §5.1 要求测试全部离线。进 CI 的是**算术本身**：
`evals/metrics.py` 的两个新增纯函数由 `tests/test_error_eval.py` 用固定假数据钉死，
评估集的结构（20 条、键集合、id 唯一、最后一行类型可解析）也由它守。

---

## 1. 跑分前的前置条件

| 条件 | 检查方式 | 不满足时的表现 |
|------|----------|----------------|
| Docker daemon 已启动 | `docker info` | `run_v2_eval` 以**退出码 2** 结束，stderr 打印"跑分无法开始：沙箱不可用：Docker daemon 未启动或 pyassist-sandbox:1 镜像缺失" |
| 沙箱镜像存在且 tag 正确 | `docker image ls pyassist-sandbox` | 同上（`build_sandbox_runner()` 返回 `None`） |
| 语料已 ingest（`data/chroma/` 有索引） | `rag/retriever.py::probe_index_depth`（**不要**用 `count()`，见 `AGENTS.md` §4） | 每条记失败，`failed_records=20`；若启动即抛 `CorpusMissing` 则退出码 2 |
| `DEEPSEEK_API_KEY` 已配置 | `.env` 或环境变量 | 退出码 2，`ConfigError` |
| 网络可达 `api.deepseek.com` | `curl https://api.deepseek.com/models` | 每条记失败，`error_type_accuracy=0.000` |
| 处于**非峰值时段** | 见 §4 | 能跑通，但 pro 档单价翻倍 |

### 评估集从哪来

`src/pyassist/evals/datasets/errors.jsonl` 的 20 条 traceback 是**真实运行**得到的，
不是手写的：`experiments/capture_error_dataset.py` 把每条 `broken_code` 写进临时目录，
用 `python -I case.py`（cwd=临时目录）跑一次，原样收 stderr。唯一归一化是去掉临时目录
前缀，免得把本机用户名和随机路径带进仓库。

脚本是**溯源记录**，不是"刷新数据集"的工具。评估集**只能新增、禁止修改已有用例**
（`AGENTS.md` §4）：已有 20 条一旦跑过分，就不能重跑脚本覆盖它们；新增用例只能追加
新记录。`tests/test_error_eval.py` 会盯住条数、键集合、id 唯一与类型可解析。

## 2. 怎么跑

```bash
# 全量（20 条）：错误类型准确率 + 修复通过率
uv run python -m pyassist.evals.run_v2_eval

# 冒烟：先跑 3 条确认链路通（Docker + key + 索引都活着），再跑全量
uv run python -m pyassist.evals.run_v2_eval --limit 3

# 换数据集（例如只跑某一批新增用例）
uv run python -m pyassist.evals.run_v2_eval --dataset path/to/errors.jsonl
```

每条记录做三件事：

1. `parse_traceback` 确定性解析 → 检索 query + 错误类型（**解析不调模型**）；
2. 跑一遍完整诊断图：≤ 3 轮工具调用（`search_docs` / `read_doc` / `explain_error` /
   `run_code`）→ 结构化修复（`llm/client.py::get_structured_output`，JSON 模式；
   不能用 `with_structured_output` 默认的 function_calling，思考模式会 400）→
   沙箱验证 → 失败带 stderr 回环重试（`MAX_REPAIR_ATTEMPTS=2`）；
3. 收集 `error_type` 与最后一次 `verification.status`。

开销量级：20 条 ×（最多 3 轮工具 + 2 次修复 + 1 次首答 = **≤ 6 次 pro 模型调用**
+ 至少 1 次容器执行）。pro 档单次在美分级，20 条全量也是美分级 —— 真正的约束是
"别在峰值跑"和"别在调试循环里反复跑全量"。

跑分图使用**临时 SQLite 检查点**（`tempfile.TemporaryDirectory`，每次运行独立
`run_id` 前缀的 thread），不碰 `data/app.db`，也不在业务表里留任何行（D12）。

## 3. 输出与判定

唯一输出行（`run_v2_eval.py::_report` 打印的就是它，`tests/test_error_eval.py`
逐字断言格式）：

```
records=20  error_type_accuracy=0.9xx  fix_pass_rate=0.7xx  timeouts=n
```

有失败记录时追加一行：

```
failed_records=2（按 0 计入上面的均值，明细见日志）
```

评估集为空时输出：

```
records=0  （评估集为空）
```

判定门槛（`AGENTS.md` §5.3 / `config.ERROR_TYPE_ACCURACY_TARGET` /
`config.FIX_PASS_RATE_TARGET`）：

| 指标 | 门槛 | 含义 |
|------|------|------|
| `error_type_accuracy` | ≥ 0.85 | 预测异常类型与 `expected_error_type` **逐条全等**的比例 |
| `fix_pass_rate` | ≥ 0.70 | 最后一次沙箱 `status == "ok"` 的比例 —— "看起来对"不算，必须跑过 |
| `timeouts` | 记录值，不设门槛 | 沙箱超时是实验结果（`data.status="timeout"`），不是服务故障 |

读法上的约定：

- **分母永远是全部用例**。异常、空检索、未验证都按 0 计入均值 —— 否则"跑挂一半"
  会表现为分数变高。
- **只归一化格式噪声**：去首尾空白、取最后一段（`json.decoder.JSONDecodeError` →
  `JSONDecodeError`，与 `parse_traceback` 一致）。大小写不归一化，`valueerror` 计错。
- **不引入 LLM 裁判**。错误类型是可判定的字符串比较；修复是否通过由沙箱退出状态决定。
- **单条 `AppError` 不中断全量**：记为失败行（`predicted=None`、`status=None`），
  按 0 计，继续下一条，明细在 `eval.record` 日志里。

## 4. 真实隔离验收（`-m docker`）

默认 `pytest` 的 `addopts` 带 `-m 'not docker'`，下面 10 条**不会**在常规回归里跑。
它们证明的是安全边界本身，而不只是"代码能执行"：

```bash
docker build -f src/pyassist/sandbox/Dockerfile.sandbox -t pyassist-sandbox:1 .
uv run pytest -m docker -v
```

| 用例 | 证明什么 |
|------|----------|
| `test_normal_execution` | 容器内 `print(6*7)` 能看到 stdout、退出码 0 |
| `test_nonzero_exit_is_a_result` | 非零退出是 **`SandboxResult`**，不是异常 |
| `test_infinite_loop_is_killed` | 死循环被超时杀掉，返回 `status="timeout"`，不拖死调用方 |
| `test_network_is_disabled` | `socket.create_connection(("1.1.1.1", 80))` 失败 |
| `test_root_filesystem_is_read_only` | 写 `/work/hacked.txt` 失败（errno） |
| `test_runs_as_unprivileged_user` | 容器内 `id` 是 `10001 10001`，不是 root |
| `test_fork_bomb_is_capped_by_pids_limit` | 进程数被 `pids_limit=64` 截住，宿主不受影响 |
| `test_rm_rf_does_not_touch_the_host` | `os.system("rm -rf /")` 后容器仍能返回结果 |
| `test_etc_passwd_read_sees_the_container` | 读 `/etc/passwd` 只看到容器自己的用户表 |
| `test_no_containers_leak_after_run` | 每次执行后容器被删除，没有 Label 残留 |

若 daemon 或镜像不可用，模块级 fixture 会 `pytest.skip` 并打印构建命令 ——
**skip 不等于通过**，结果记录里必须如实写"未验证"。

## 6. 低于门槛时先看什么

按顺序排查，**不要**一上来调阈值或改评估集：

1. **`eval.record` 日志的 `error` 字段**。若整批都是 `ConfigError` / `CorpusMissing`，
   是环境问题，不是模型问题；先修环境再谈分数。
2. **`error_type_accuracy` 低**：先看 `parse_traceback` 对最后一行类型的解析是否被
   链式异常（`During handling of the above exception...`）或 `json.decoder.` 前缀干扰。
   解析是确定性的，查得出就是 bug，不是"运气不好"。
3. **`fix_pass_rate` 低但 `error_type_accuracy` 高**：看沙箱 `stderr` —— 是修复代码本身
   错了（模型问题），还是缺依赖 / 超时（环境问题）。`timeouts` 单独计数就是为了
   区分这两类。
4. **最后才考虑提高 `MAX_REPAIR_ATTEMPTS`**。每次多一轮 = 多一次 pro 调用 + 一次容器
   执行；用数据决定（§10 第 8 条），不要为了提分无限重试。
5. **禁止**为了提分挑选简单用例、修改已有 traceback 或改 `metrics.py` 的判定规则 ——
   这是本项目最严重的作弊（`AGENTS.md` §4、SPEC §4）。
